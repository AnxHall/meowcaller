### WebRTC/DTLS/SCTP data channels

The enhanced extension directly confirms the browser transport that the earlier
capture could only infer:

1. PCs 1–2 are a short-lived `sctp-prewarm` pair before the call.
2. PC 3 is a `__transfer_probe__` and closes immediately.
3. PCs 4–9 each create a negotiated, unordered, zero-retransmit
   `pre-negotiated` data channel.
4. PCs 4/6/8 connect over IPv4 UDP to zrh1/mxp2/fra5.
5. PCs 5/7/9 are the corresponding IPv6 attempts; they remain `new`, transfer
   no bytes, and close after about 20 seconds.

All six relay SDPs have only:

```text
m=application 9 UDP/DTLS/SCTP webrtc-datachannel
a=sctp-port:5000
a=max-message-size:262144
```

There are no browser RTP audio/video tracks on these peer connections. WhatsApp
encapsulates its own WARP/SRTP datagrams in the data channel.

All relay remote descriptions use the same ICE username fragment and DTLS
fingerprint while presenting different relay IP candidates. This is evidence
that they are endpoints of one logical relay service/allocation, not six media
peers.

- SRTP transports attach per participant SSRC and payload type.

SFrame key-slot functions execute, but active SFrame stream protection is not

## Comparison with current implementations

### Refreshed whatsmeow

The refreshed whatsmeow branch remains 1:1-oriented:

- `calls.go` builds one peer offer and public methods address one call peer.
- `call.go` parses `GroupJID` as metadata but has no group roster/PID state
  machine.
- There is no `group_update` transaction handling, group participant rekey
  ownership, call-route lifecycle, group `connect_stat`, or final group summary.
- Relay parsing/election exists, but the current public media handoff does not
  preserve the observed participant UUID/PIDs, HBH key, group transaction, or
  dynamic WARP tag-length state.

The capture says these belong to call control: authoritative roster transitions,
device selection, group transactions, participant rekeys, and shared
audio/video group state must be represented before meowcaller can consume a
stable group-media description.

### Meowcaller thin rebuild

The current meowcaller media plane remains one-self/one-peer:

- `session.go` holds one send pipeline and one receive pipeline; a receive
  rekey replaces one peer keystream.
- `engine_media.go` derives one self/peer descriptor pair, one remote audio
  stream, and one remote video stream.
- SSRC derivation and RTP/SRTP/SRTCP/WARP primitives are KAT-covered and the
  observed call-ID/device-dependent SSRC behavior is consistent with them.
- WARP tag length is fixed at four; this trace matches four but also proves it
  is signaled state.
- SFrame/HBH primitives exist but are not in the production path. This trace's
  disabled SFrame flags provide no reason to change that.
- The relay client needs one elected endpoint for media, but group support also
  needs the full candidate set long enough to probe/elect and preserve
  participant/PID/key metadata.

Required group-media abstractions evidenced here are:

1. a participant/device roster keyed by LID and PID;
2. participant-owned 32-byte key slots/epochs;
3. per-participant audio, video-0/video-1, app-data, and screen-share SSRC plans;
4. one shared WARP relay transport with participant-specific subscriptions and
   demultiplexing;
5. independent remote audio/video state and sinks;
6. participant-aware audio mixing and video routing;
7. group-wide media mode that does not collapse independent participant camera
   state.

No existing 1:1 behavior should be changed solely from this observation.

## Observed conclusions

1. One logical call uses a central `call-id@call` route plus
   participant-addressed transport and rekey stanzas.
2. Device selection resolves multiple offered devices to one PID-bearing active
   device per user.
3. PIDs 0/1/2 bind stable, distinct per-participant SSRC plans.
4. One WARP SFU allocation exposes three regional relay endpoints. The browser
   connects to all IPv4 endpoints but elects zrh1 for the media path.
5. WhatsApp media is carried as custom datagrams over negotiated SCTP data
   channels, not as WebRTC audio/video tracks.
6. Worker-event byte/message totals exactly match the aggregate browser
   data-channel statistics.
7. Group rekey processing retains existing participant slots and adds the newly
   connected participant's key.
8. Mute and video states are participant-specific. Shared `media=video` does not
   mean every camera is enabled.
9. MLow audio, H.264 video, E2E SRTP machinery, and WARP/SFU are active.
   SFrame stream protection remains disabled.
10. The call ends normally; no join/leave test beyond initial joining is present.

## Hypotheses and unresolved questions

- Relay-latency high bits likely encode flags and the low portion milliseconds;
  this needs source or additional vectors.
- The two 32-byte values appear to be sender/participant chain keys. The final
  KDF and epoch semantics remain unproven.
- Worker records classified as `stun` likely include WARP-framed media/control,
  but only a validated WARP parser can divide them precisely.
- The three short connected relay channels may be an election strategy in which
  all IPv4 candidates complete bind probes before one carries media.
- `audio_duration` and `video_duration` appear to partition group media phases,
  not simultaneous media activity.
- The meaning of call reason code 2, transport type 4, protocol 0, network
  medium numbers, and call-model numeric states remains implementation-private
  unless corroborated by source.
- No late join, remote leave, participant removal, downgrade, screen share,
  reaction, app-data payload, relay failover, IPv6 success, or rejoin occurs.
