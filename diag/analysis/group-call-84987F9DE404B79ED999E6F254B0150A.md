## Confirmed failure mechanism

`relay.ClassifyRelayPacket` classifies by the first byte of the data-channel
message. The `0x09` group-forwarding marker has its top two bits clear, so the
current code labels all 986 packets as STUN. They fail STUN parsing and are
dropped before RTP parsing, participant SSRC lookup, SRTP authentication, H.264
depacketization, or audio decode.

This exactly explains the reported UI behavior:

1. one participant works while the relay sends ordinary RTP;
2. the second participant connects and the relay changes its downlink format;
3. Meowcaller receives traffic but emits no new frames;
4. when the roster returns to one participant, ordinary RTP resumes and video
   appears to unfreeze.

## Implementation hypothesis

The capture supports a bounded de-framer:

- marker `0x09`, subtype 2: strip 8 bytes;
- marker `0x09`, subtype 4: strip 12 bytes;
- marker `0x09`, subtype 7: strip 18 bytes;
- require a complete RTP header and RTP version 2 after the prefix;
- drop unknown or malformed `0x09` envelopes;
- pass non-`0x09` packets through unchanged.

The fixed offsets are authoritative for all 986 packets in this capture. The
resulting inner packets have the exact participant SSRCs and uninterrupted
sequence spaces expected by the existing receive registry. Restored live
multi-participant audio/video remains the end-to-end acceptance test.
