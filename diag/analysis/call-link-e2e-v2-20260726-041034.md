## Executive conclusion

This capture contains the complete missing control flow for a new video call
link:

1. create the link;
2. preview/query it;
3. join with approval disabled;
4. start a second active session from the same link;
5. enable approval;
6. request entry from a second account;
7. deny that request;
8. request entry again;
9. admit the requester; and
10. establish relay media and rotate group keys after admission.

The opaque link token identifies the reusable link, not an active call. The same
token first resolves to call ID `0067CBB85B113E16600396BD25346DB3`, then to
`00AF16E8F3C700B81311EE5A19EA7531` after the first session ends. All
call-scoped waiting-room actions route to the current `CALL_ID@call`.

The capture proves approval enable, deny, and admit. It does not contain an
`enabled="0"` toggle, `waitingRoomAdmitAll`, link revocation, or audio-link
creation.

## Link creation

Creation is a small service-level request. It has no call ID:

```xml
<call id="65149.29747-11" to="call">
  <link_create media="video" />
</call>
```

The typed ACK returns the new token:

```xml
<ack from="call" class="call" type="link_create" id="65149.29747-11">
  <link_create media="video" token="PNtK9cGQ1OrmsKqnWPo0wN" />
</ack>
```

This establishes a clean API boundary: create returns a reusable token/URL but
does not itself establish media or allocate an active call.

## Preview and join

Preview sends `link_query` to the call service using only the token and media
type. The ACK returns:

- bare creator LID and creator phone-number JID;
- token and media type;
- whether approval is enabled; and
- `is_admin=1` only for the creator's account.

Joining is separate:

```xml
<link_join token="PNtK9cGQ1OrmsKqnWPo0wN" media="video">
  <audio enc="opus" rate="16000" />
  <video dec="H264" device_orientation="0" />
  <net medium="2" />
  <capability ver="1">...</capability>
</link_join>
```

When approval is disabled, the `link_join` ACK contains `group_info`, waiting-room
metadata with `enabled="0"`, field-stat settings, and VoIP settings. The ordinary
group-update/relay/key flow then starts immediately.

When approval is enabled, the same request receives only:

```xml
<waiting_room
  link-token="PNtK9cGQ1OrmsKqnWPo0wN"
  media="video"
  call-id="00AF16E8F3C700B81311EE5A19EA7531"
  call-creator="156535032389744:15@lid"
  enabled="1" />
```

There is no relay allocation or `group_info` for the requester until admission.
The pending client sends ordinary `heartbeat` stanzas with
`type="waiting_room"`.

## Enabling approval

The active-call API call `waitingRoomToggleActiveCall(true)` becomes:

```xml
<call to="00AF16E8F3C700B81311EE5A19EA7531@call" id="65149.29747-29">
  <waiting_room_toggle
    call-id="00AF16E8F3C700B81311EE5A19EA7531"
    call-creator="156535032389744:15@lid"
    enabled="1" />
</call>
```

The server sends a typed ACK and then an authoritative
`waiting_room_update enabled="1"` to the administrator.

The earlier capture began with approval disabled and this capture proves the
transition to enabled. It does not contain a toggle request with `enabled="0"`,
so disable must remain an evidence-backed scaffold using the symmetric shape,
not be marked verified yet.

## Denial

The administrator receives a transactioned waiting-room roster:

```xml
<waiting_room enabled="1" transaction-id="2" is_admin="1" ...>
  <user jid="242653052539031@lid" state="waiting_room_joined" ... />
</waiting_room>
```

Denial names the bare user LID:

```xml
<waiting_room_deny call-id="00AF..." call-creator="156535032389744:15@lid">
  <user jid="242653052539031@lid" />
</waiting_room_deny>
```

The requester receives `terminate transaction-id="-1"
reason="waiting_room_deny"`. The administrator then receives a roster update
with state `waiting_room_terminated`. The link remains valid: the same user
queries and requests entry again a few seconds later.

## Admission, relay, and keying

Admission uses the same routing and user selector:

```xml
<waiting_room_admit call-id="00AF..." call-creator="156535032389744:15@lid">
  <user jid="242653052539031@lid" />
</waiting_room_admit>
```

The ACK only confirms the control action. Successful promotion is conveyed by
ordinary group-call updates:

- requester receives transaction 3 with both users connected, PID 1 for itself,
  relay UUID `0EWNIeOLOxQj2z4y`, participant UUID, and its relay credentials;
- administrator receives transaction 3 with both users connected, PID 0 for
  itself, its relay allocation, and `rekey="1"`;
- administrator then receives waiting-room transaction 5 with no pending users.

This means admission should not create a parallel media path. It should hand the
participant into the existing group membership, relay, and key machinery.

## Stable link token versus active call ID

One token produces two active call IDs in this capture:

| Link token | Active call | Approval |
|---|---|---|
| `PNtK9cGQ1OrmsKqnWPo0wN` | `0067CBB85B113E16600396BD25346DB3` | disabled |
| `PNtK9cGQ1OrmsKqnWPo0wN` | `00AF16E8F3C700B81311EE5A19EA7531` | enabled after creator joins |

Implementations must therefore keep `linkToken` and `callID` as separate fields.
Preview and initial join are token-scoped; waiting-room controls, heartbeats,
group updates, relay setup, and media are call-ID-scoped.

## Current implementation gap

The local `rajeh/group-calls` whatsmeow branch has protobuf fields for call-log
records (`IsCallLink` and `CallLinkToken`) but no call-control implementation for:

- `link_create`, `link_query`, or `link_join`;
- call-link state and preview results;
- `waiting_room_toggle`, `waiting_room_update`, `waiting_room_admit`, or
  `waiting_room_deny`;
- pending-request heartbeats; or
- typed public lifecycle events for waiting-room changes.

The local meowcaller branch and web example contain no call-link or waiting-room
surface. Existing group membership, relay setup, rekey handling, H.264, and Opus
paths can be reused only after a joiner receives admitted `group_info`.

The implementation boundary supported by this capture is:

1. **whatsmeow call control:** create/query/join link requests, typed ACK parsing,
   token-to-active-call context, pending heartbeats, toggle/admit/deny requests,
   waiting-room roster events, and denial termination.
2. **meowcaller media plane:** remain dormant while pending, then consume the
   ordinary admitted group update, relay allocation, participant PID/SSRC map,
   and rekey.
3. **web example:** create video/audio link controls, URL/token preview, join,
   explicit waiting state, approval toggle, pending-user roster, deny/admit
   actions, and transition from waiting UI to the existing group-call media UI.

## Observed facts versus hypotheses

### Observed

- `link_create` returns a reusable opaque token and no call ID.
- `link_query` reports creator, media, approval state, and administrator status.
- `link_join` carries media capabilities.
- Approval-off join returns group context and enters the call immediately.
- Approval-on join returns only waiting-room call context.
- Pending clients send `heartbeat type="waiting_room"`.
- Administrators receive transactioned `waiting_room_update` rosters.
- Denial terminates the requester with `reason="waiting_room_deny"`.
- The denied user can request entry again using the same link.
- Admission promotes the requester through ordinary group update, relay, and
  rekey flows.
- The stable token maps to a different call ID after the first active session
  ends.

### Hypotheses and unobserved cases

- Disable uses `waiting_room_toggle enabled="0"`. The symmetry is strong but the
  request itself was not captured.
- Audio links use the same topology with `media="audio"` and omit the video
  capability child.
- Waiting-room heartbeats keep the request alive until admit, deny, timeout, or
  departure.
- `waitingRoomAdmitAll` likely sends a distinct control child or an admit request
  containing multiple users; neither form was observed.
- Link revocation, expiration, ownership transfer, and waiting-room timeout
  remain unknown.
